# 线程绑核测试(隔离CPU4-7情况下进行的测试)

这个程序用 GTest 自动检查 10 个绑核场景：接口有没有成功、线程允许在哪些 CPU 上运行、实际跑在哪个 CPU 上。
在 Ubuntu 主机上编译，放到 RK3576 板子上运行，不需要启动业务程序，也不用烧录固件。

注意：绑核是限制线程能在哪些核上运行，不是隔离 CPU。这个测试不会修改设备树或 CPU 隔离配置。

## 1. 编译（Ubuntu 主机）

已经有 `out/bin/hc_gtest_thread_affinity`、且不需要更新时，可以跳到第 2 步。

第一次编译可用工程现有脚本，会编译全部 GTest，并开启代码覆盖率记录：

```bash
cd /home/jihongxin/Documents/douhe/develop
export PATH=/opt/rk3588/arm-gnu-toolchain-11.3.rel1-x86_64-aarch64-none-linux-gnu/bin:$PATH
./build.sh dubhe --gtest
```

如果 `tmp` 已经按上述 GTest 模式配置好，后续只编译绑核测试即可：

```bash
cmake --build tmp --target hc_gtest_thread_affinity -j 8
```

生成文件：`out/bin/hc_gtest_thread_affinity`。这是 ARM64 板端程序，不能直接在普通 x86 Ubuntu 上运行。
工程配置仍使用 RK3588 名称；在 RK3576 上使用前，要按第 3 步检查运行库。不要混用其他产品或工具链的 `tmp` 缓存。

## 2. 上传（Ubuntu 主机）

## 3. 运行全部 10 项（板子）

先检查程序依赖：

```sh
cd /tmp/thread-affinity-test
chmod +x hc_gtest_thread_affinity
ldd ./hc_gtest_thread_affinity
```

如果出现 `not found` 或库版本错误，先解决运行库问题，不要覆盖板子的系统库。板端不需要另装 GTest 或 libnuma。
确认 CPU0–7 在线，且测试没有被 cpuset/cgroup 禁止使用这些核；不要与正式的 cyclictest 延迟测试同时运行。

运行并自动保存日志、打包结果：

```sh
GTEST_BIN_DIR=/tmp/thread-affinity-test sh ./gtest_run.sh --verbose hc_gtest_thread_affinity
echo "Exit code: $?"
```

正常情况下约 16 秒跑完，具体时间受系统调度影响。
脚本会清理前次 GTest 结果和覆盖率数据；需要保留时，先按第 5 步下载。

## 4. 看结果（板子）

```sh
cat /userdata/gtest/details/hc_gtest_thread_affinity/test-result.txt
tail -n 30 /userdata/gtest/details/hc_gtest_thread_affinity/gtest.log
```

| 输出 | 意思 |
| --- | --- |
| `[ PASSED ] 10 tests.` | 10 项全部通过；同时确认退出码为 0、没有失败或跳过 |
| `FAILED` | 有用例失败，查看日志中的具体原因 |
| `SKIPPED` | 缺少测试条件，例如目标 CPU 不在线，不算通过 |
| `tid=...` | 当前线程编号 |
| `affinity={7}` | 这个线程只允许在 CPU7 上运行 |
| `running_cpu=7` | 这次采样时，线程正在 CPU7 上运行 |

`affinity={5,6,7}` 表示允许在这三个核中的任意一个运行，不要求每个核都跑到。
用例 2、3、5 通过，表示旧接口的行为符合预期，不表示旧接口能绑定调用它的子线程。
功能测试通过和代码覆盖率达标是两回事。

## 6. 只跑其中一项（板子，可选）

例如只跑第 1 项：

```sh
cd /tmp/thread-affinity-test
mkdir -p coverage
export GCOV_PREFIX=/tmp/thread-affinity-test/coverage
export GCOV_PREFIX_STRIP=0
./hc_gtest_thread_affinity 1
echo "Exit code: $?"
```

把 `1` 换成 `2`～`10` 就能选择其他项；不加编号则跑全部 10 项。
第 1 项中，主线程和子线程都应显示 `affinity={7} running_cpu=7`。
这种直接运行方式只在终端显示日志，不会自动生成第 5 步的压缩包。

## 10 个测试场景

每项开始先把主线程设为允许在 CPU0–3 上运行。子线程创建时，会继承创建者的允许 CPU 集合。
表中的“默认”指测试设置的 CPU0–3，不是系统默认配置；用例结束后恢复主线程原来的设置。

| 编号 | 怎么测 | 最终主线程允许的 CPU | 最终子线程允许的 CPU |
| --- | --- | --- | --- |
| 1 | 主线程用旧接口绑 7，再创建不绑核的子线程 | `{7}` | `{7}` |
| 2 | 主线程默认，子线程用旧接口绑 7 | `{7}` | `{0,1,2,3}` |
| 3 | 主线程先绑 6，子线程用旧接口绑 7 | `{7}` | `{6}` |
| 4 | 主线程用旧接口绑 4–7，再创建不绑核的子线程 | `{4,5,6,7}` | `{4,5,6,7}` |
| 5 | 主线程默认，子线程用旧接口绑 4–7 | `{4,5,6,7}` | `{0,1,2,3}` |
| 6 | 只有主线程，用旧接口绑 7 | `{7}` | 无 |
| 7 | 只有主线程，用旧接口绑 4–7 | `{4,5,6,7}` | 无 |
| 8 | 三个子线程用新接口分别绑 5、6、7 | `{0,1,2,3}` | 分别为 `{5}`、`{6}`、`{7}` |
| 9 | 三个子线程用新接口分别绑 5、6、5–7 | `{0,1,2,3}` | 分别为 `{5}`、`{6}`、`{5,6,7}` |
| 10 | 前四个子线程不绑核，后四个用新接口分别绑 4、5、6、7 | `{0,1,2,3}` | 前四个各 `{0,1,2,3}`；后四个分别为 `{4}`、`{5}`、`{6}`、`{7}` |

新旧接口最重要的区别：

- 旧接口 `hc_platform_bind_core()` / `hc_platform_bind_cores()`：改的是主线程，即使在子线程里调用也是如此，不是修改整个进程的所有线程。
- 新接口 `hc_platform_bind_current_thread_core()` / `hc_platform_bind_current_thread_cores()`：谁调用就改谁，子线程调用就只改这个子线程。
